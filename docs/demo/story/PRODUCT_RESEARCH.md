# Product research: prompt portfolio → experiments → promotion → session

Checked 2026-10-08 against official Langfuse documentation, including the v4 evaluator migration guidance. This is public product research for a fictional financial-services prompt portfolio, not an acceptance record or a live deployment verification. Feature availability and interaction details must be rehearsed against the eventual demo server and plan.

Classification: **Native** means documented Langfuse behavior; **Integration** means application or delivery tooling must supply behavior; **Unverified** means these sources do not establish the requested guarantee, not proof that it is impossible.

## Capability boundaries

| Capability | Finding and demo implication | Primary source |
| --- | --- | --- |
| Central prompt library and folders | **Native.** Slash-separated prompt names form virtual folder hierarchies. Use a small library such as `shared/`, `assistant/`, and `content/`; folders alone do not establish a permission boundary. | [Folders](https://langfuse.com/docs/prompt-management/features/folders), [RBAC](https://langfuse.com/docs/administration/rbac) |
| Find prompts by their content | **Native, release evidence.** Full-text prompt-content search was announced 2025-07-22, extending name/tag search. Confirm current search scope and UI in rehearsal; the announcement does not establish cross-project or every-historical-version search. | [Full-text prompt search announcement](https://langfuse.com/changelog/2025-07-22-full-text-search-for-prompts) |
| Shared instruction blocks | **Native.** Prompts can reference other **text prompts**, pinned by version or dynamically resolved by label. The latter lets shared changes affect dependents. Arbitrary nested depth, cycle behavior, dependency snapshots, and automatic impact analysis remain **unverified** from this documentation. Begin with one reusable block and explicit version pins for comparison. | [Prompt composability](https://langfuse.com/docs/prompt-management/features/composability) |
| Conditional composition | **Integration.** Select sub-prompts in application code and insert the chosen text via a variable. This application logic is not automatically executed in the Playground or UI prompt experiments. Do not silently model conditional application behavior as a native prompt experiment. | [Conditional prompt embedding](https://langfuse.com/faq/all/conditional-prompt-embedding) |
| Variables and validation | **Native:** `{{variable}}` string substitution in text/chat prompts through compilation. The editor announcement (2025-01-30) establishes inline warnings for invalid variable names and JSON syntax. A general typed variable schema, required-variable enforcement across every SDK/runtime path, or business-rule validation remains **unverified**; put such checks in application/test logic unless separately verified. | [Variables](https://langfuse.com/docs/prompt-management/features/variables), [Editor announcement](https://langfuse.com/changelog/2025-01-30-new-prompt-editor) |
| Version history, release and rollback | **Native.** Versions, diffs and movable labels support staged selection and rollback. Fetching by label follows its current version; fetching by version pins it. Moving `production` back releases an older version. **Inference:** an application already fetching a compatible prompt by label can change prompt text without an application deployment. This is not a guarantee for code/schema/model changes. | [Version control](https://langfuse.com/docs/prompt-management/features/prompt-version-control) |
| Cache-aware rollout | **Native.** SDK caching defaults to 60 seconds and serves stale values while refreshing asynchronously after expiry. Cache misses fetch from the API; fallback prompts are optional. Promotion/rollback therefore is not an instantaneous fleet-wide switch. For a controlled non-production demo, TTL zero can show a fresh fetch; separately explain production caching. | [Caching](https://langfuse.com/docs/prompt-management/features/caching) |
| Prompt experiments | **Native.** UI experiments compare prompt versions/models on datasets, with optional managed code or LLM-as-a-judge scoring. They require an LLM connection and dataset input keys matching prompt variables/placeholders. Historical dataset versions can be selected; otherwise latest is used. Variables inside placeholder messages are not resolved. | [Experiments via UI](https://langfuse.com/docs/evaluation/experiments/experiments-via-ui) |
| Comparable evidence | **Native comparison; team-defined decision.** Compare runs on the same dataset version and evaluator definitions, inspect individual regressions, and open failing-item traces. Record prompt/model/application/evaluator versions. Dataset versioning fixes test inputs, not model determinism. An average improvement alone is insufficient release evidence. | [Compare experiments](https://langfuse.com/docs/evaluation/experiments/compare-experiments) |
| Exact prompt → generation link | **Native with instrumentation.** Attach the fetched prompt object to the intended generation. The UI exposes the used prompt and per-version metrics. This relationship must be recorded; fetching a prompt alone is not proof every downstream generation is linked. A parent version link does not by itself prove a complete immutable snapshot of dynamically resolved dependencies. | [Link prompts to traces](https://langfuse.com/docs/prompt-management/features/link-to-traces), [Prompt composability](https://langfuse.com/docs/prompt-management/features/composability) |
| Stage permissions | **Native, plan-dependent.** Protected labels restrict modification/deletion to admins/owners; members/viewers cannot move them. Project-level roles are also plan-dependent. Prompt labels are not automatically separate security environments. Project API keys are project-scoped and not user identities. Verify API enforcement before making a security guarantee. | [Protected labels](https://langfuse.com/docs/prompt-management/features/prompt-version-control#protected-prompt-labels), [RBAC](https://langfuse.com/docs/administration/rbac) |
| Four-eyes approval and automated gates | **Integration / native enforcement unverified.** Protected labels do not establish author/approver inequality, two approvals, or mandatory successful evaluations. Official CI guidance supplies experiment scripts and regression failures; teams configure delivery gates. Prompt webhooks can dispatch GitHub workflows. Demonstrate an external gate only if actually implemented and validated. | [Experiments in CI/CD](https://langfuse.com/docs/evaluation/experiments/experiments-ci-cd), [GitHub integration](https://langfuse.com/docs/prompt-management/features/github-integration), [Protected labels](https://langfuse.com/docs/prompt-management/features/prompt-version-control#protected-prompt-labels) |
| Change accountability | **Native, Enterprise.** Audit logs identify user/API-key actor, timestamp, action and before/after state. Listed prompt actions include create, delete, promote, setLabel, update and updateTags. Audit history records actions; it does not itself enforce approval. | [Audit logs](https://langfuse.com/docs/administration/audit-logs) |
| Reverse dependency impact analysis | **Unverified.** The reviewed composability documentation establishes references but not a complete reverse graph, affected-application inventory, or safe shared-block rollout analysis. If needed, build an explicit demo-owned dependency inventory and label it as such; do not present it as an existing Langfuse screen. | [Prompt composability](https://langfuse.com/docs/prompt-management/features/composability) |

## Session, score and evaluator boundaries

| Question | Finding and implementation consequence | Primary source |
| --- | --- | --- |
| Can the prompt Metrics tab display scores? | **Native:** its documented aggregates include median score value alongside generation latency, tokens, costs and count, grouped by prompt version. Attach the prompt and relevant score to the actual generation. Support for every arbitrary score type/source, and automatic rollup from root or session scores, is **unverified**. Rehearse each chosen metric rather than promising universal score visibility. | [Prompt Metrics reference](https://langfuse.com/docs/prompt-management/features/link-to-traces#metrics-reference) |
| Is the session a native conversation entry point? | **Native:** shared `sessionId` values group observations and their traces into session replay; the UI supports session annotations. Propagate the identifier early across all relevant observations. The precise chat layout, per-turn drill-down and automatic display of each observation score beside a message remain **unverified** from these docs and need UI inspection. | [Sessions](https://langfuse.com/docs/observability/features/sessions) |
| Where can the presenter inspect individual evaluations? | **Native:** observation detail exposes score values and judge reasoning; manual scores have a Scores tab on trace/observation detail. Use session replay as the navigation anchor, then select the relevant turn/observation when needed. Session annotations and per-turn observation scores have different subjects; do not relabel one as the other. | [Live evaluation results](https://langfuse.com/docs/evaluation/get-started/online#see-scores-on-production-traces), [Scores via UI](https://langfuse.com/docs/evaluation/evaluation-methods/scores-via-ui) |
| Can experiments and live traffic reuse a rubric? | **Native:** the evaluator defines rubric/model/score and mappings; live rules select observations and can override mappings. The same evaluator can run in prompt experiments. Live mappings read the selected observation's input/output/metadata/tool calls; expected output and experiment item metadata are offline-only. Keep identical rubric meaning where evidence is equivalent, and record any intentional offline-only criterion separately. | [LLM-as-a-Judge targets and mappings](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge) |
| How does v4 change score placement? | A trace groups observations; input/output belong to observations. Each matched observation receives its own score. Select a stable observation name/type/root filter to avoid accidentally scoring several operations per turn. Experiment migration maps old dataset context to experiment-item context. The current official guide uses stable APIs and `experimentDatasetId`; implementation must follow the then-current schema, not older bundled notes referring to unstable APIs or `datasetId`. | [v4 data model](https://langfuse.com/docs/observability/data-model), [Evaluator migration](https://langfuse.com/faq/all/llm-as-a-judge-migration) |
| Does a session ID give a judge the conversation? | **No automatic context join.** Managed judges cannot target sessions directly. For conversation-aware evaluation, target an observation that actually contains the history, either each turn or a deliberately marked final turn. The resulting managed score belongs to that observation; separately created scores may target the session itself. | [Evaluating sessions and conversations](https://langfuse.com/resources/engineering/evaluating-sessions-conversations) |
| Can input and output evaluation stay separate? | **Native primitives; demo-owned mapping.** An input-only evaluator can read the current user message and omit assistant output. A response evaluator reads the reply plus required context. Both may attach to the same observation with distinct score names; separate judgments do not require artificial trace records. Code evaluators read `ctx.observation` directly and have optional experiment context, with no separate variable-mapping step. | [Judge variable mapping](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge#map-variables), [Code evaluator context](https://langfuse.com/docs/evaluation/evaluation-methods/code-evaluators#context-fields) |

**Design recommendation:** preserve role-bearing model input and actual assistant output. Expose the current user message explicitly on the selected observation, for example in metadata; do not assume automatic last-user-message extraction. Keep prior turns separate when a rubric needs conversational context. A message-only judgment cannot establish what earlier turns mean. Judges do not join sibling/child observations. [Observation evaluator scope](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge#data-available-to-observation-level-evaluators)

## Implications for the current journey

The chosen narrative is a fictional financial-services prompt portfolio → experiment comparison → admin promotion → chatbot session. This note supports that direction without acting as its acceptance record.

1. **Open the portfolio.** Establish central ownership, reusable instructions and versions. Use actual prompt/generation associations where prompt-level score evidence is shown.
2. **Compare experiments.** Review the chosen candidate and comparison runs on stable cases. A bad baseline, forced regression and subsequent correction loop are not prerequisites. Separate input characteristics from output judgments.
3. **Promote as an administrator.** Show the actual label change after reviewing evidence, including the role boundary. This demonstrates an authorised promotion; do not imply native four-eyes approval or automatic score gating.
4. **Use the chatbot, then open its session.** Follow the conversation in session replay as the primary navigation. Inspect the relevant observation for detailed input/output scores, reasoning and exact prompt version when helpful. The presenter chooses how to respond to the evidence; no automatic rewrite, rollback or alert is implied.

Promotion remains subject to cache refresh. Full dependency analysis and governance integrations stay outside native claims until separately verified.

## Prototype checks still required

- Confirm the target server version, plan, permissions, current UI routes and prompt-content search behavior.
- Verify the chosen composed-prompt example resolves in both UI experiments and application fetching; inspect the recorded dependency information before claiming reproducibility across shared-block changes.
- Verify dataset version, evaluator target and exact generation/prompt link with one small example; confirm that each chosen custom score appears in the intended prompt metric view.
- Rehearse session replay → turn/observation → score reasoning navigation on the target UI. Confirm which scores are visible directly in the session and which require drill-down.
- Preview the resolved input-only and output-evaluator mappings on an experiment case and a live-style turn. Check current message versus history, one intended target per turn, and absent offline ground truth on live data.
- Verify a member cannot promote a protected label and document how any automation authenticates; do not equate UI restrictions with an independently tested API policy.
- Confirm cache behavior during promotion/rollback. No live project was mutated or tested during this research.
